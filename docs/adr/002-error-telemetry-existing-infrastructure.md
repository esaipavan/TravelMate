# ADR-002: Error telemetry using the existing bug_reports table

**Date:** 2026-07-30
**Status:** Accepted

---

## Context

The application had no automatic error telemetry — production failures were silent.
The existing codebase includes:

- `bug_reports` table (user-submitted bug reports with `title`, `description`,
  `severity`, `status`, `browser_info`, `user_id` columns)
- `AdminBugsPage` at `/admin/bugs` for reviewing reports
- `ErrorBoundary` component with `componentDidCatch` that only logged to the console
- No mechanism to capture window-level JS errors or unhandled promise rejections

The requirement was to capture these automatically in production.

---

## Decision

Extend the existing `bug_reports` table and `ErrorBoundary` rather than introducing
an external observability service.

**Implementation:**

1. **`src/lib/error-reporter.ts`** — a pure TypeScript module (no React) with a
   synchronous public API: `reportError(report): void`. The actual DB write is
   fire-and-forget to avoid blocking the callsite. Uses `useAuthStore.getState()`
   (Zustand's escape hatch) to read the current user ID without needing React context.

2. **`src/components/providers/ErrorReporter.tsx`** — a zero-render React component
   mounted once in `Providers.tsx` that registers `window.error` and
   `window.unhandledrejection` listeners for the application lifetime.

3. **`src/components/shared/ErrorBoundary.tsx`** — `componentDidCatch` now calls
   `reportError` in production, capturing React render tree errors with the
   component stack.

**Rate limiting:** The same error (matched by title + first 150 chars of description)
is reported at most once per 30-second window, with a maximum of 50 distinct keys
tracked in memory. This prevents cascading failures from flooding the `bug_reports`
table.

**Safety properties:**

- Never throws — errors inside the reporter are silently swallowed
- No-op in development — errors surface naturally in the console and DevTools
- Non-blocking — all DB writes are fire-and-forget via `void async IIFE`
- Bounded memory — the deduplication map is capped at 50 keys

---

## Consequences

**Positive:**

- Zero new dependencies — reuses existing Supabase client, `bug_reports` table,
  and existing admin UI
- Automatic error capture from day one of production deployment
- Admins can review errors alongside user-submitted bug reports in one place
- Production only — development workflow is unchanged

**Negative / trade-offs:**

- **No aggregation:** The same error for 1000 users creates 1000 rows (after the
  30-second dedup window expires). There is no grouping, occurrence count, or
  "resolved" workflow. The admin UI will become noisy at scale.
- **No stack trace symbolication:** Errors from minified production bundles show
  mangled function names. Source maps are generated by the Vite build but not
  uploaded anywhere for symbolication.
- **No alerting:** Errors are written to the DB but nothing triggers a notification
  when error rates spike.
- **Not a replacement for observability:** This solution is appropriate for early
  production and small teams. It degrades gracefully — errors still show in the
  admin UI — but does not scale to high error volumes.

**Migration path:** When error volume warrants it, introduce Sentry. The `reportError`
function is the single injection point — replacing its body with a `Sentry.captureException`
call is a one-file change that requires no updates to any component.

---

## Alternatives Considered

**Sentry**
The industry standard. Provides grouping, symbolication, release tracking, alerting,
performance monitoring, and session replay. Would require `@sentry/react` +
`@sentry/vite-plugin` (adds ~30KB to the bundle), a Sentry account, and uploading
source maps at build time. Appropriate when error volume grows beyond what the
`bug_reports` table can usefully surface. Deferred — not because it is wrong, but
because it is more than currently needed.

**LogRocket / Datadog RUM**
Higher capability, higher cost, higher complexity. Same reasoning as Sentry.

**Leaving errors silent**
Rejected. Silent production failures are unacceptable for any product intended for
real users.
